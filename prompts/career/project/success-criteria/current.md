# 웹개발 프로젝트 경력기술서 작성 성공 기준

> 목표: 프로젝트 경험을 효과적으로 정리하여 채용 담당자와 면접관에게 명확하게 전달

---

## 📊 Level 1: 필수 요소 (Must-have)

### 정량적 기준
- [ ] 각 프로젝트당 200-400자 분량 (간결하면서도 충분한 정보)
- [ ] 최소 3가지 이상의 구체적 기술 스택 명시
- [ ] 최소 1개 이상의 정량적 성과 지표 포함 (사용자 수, 성능 개선율, 개발 기간 등)

### 정성적 기준
- [ ] 프로젝트 배경/문제 → 해결 방법 → 결과의 스토리 구조
- [ ] 기술 용어가 정확하고 과장되지 않음
- [ ] "담당", "참여" 같은 모호한 표현 대신 "개발", "설계", "구현" 등 구체적 동사 사용

---

## 🎯 Level 2: 차별화 요소 (Should-have)

### 임팩트 명확성
- [ ] 비즈니스 임팩트와 기술적 임팩트를 모두 기술
  - 예: "페이지 로딩 속도 40% 개선 → 이탈률 15% 감소"
- [ ] 내가 맡은 역할과 기여도가 명확함
  - 예: "3인 팀에서 백엔드 API 전체 설계 및 구현 담당"

### 기술적 깊이
- [ ] 단순 기술 나열이 아닌, "왜 그 기술을 선택했는지" 맥락 포함
- [ ] 기술적 도전과제와 해결 방법 언급
  - 예: "동시 접속자 급증에 대비한 Redis 캐싱 전략 도입"

---

## ⭐ Level 3: 인상적인 차이 (Nice-to-have)

- [ ] GitHub 링크, 데모 사이트, 포트폴리오 등 증빙 자료 첨부
- [ ] 프로젝트를 통해 배운 점/성장한 점 간략히 언급
- [ ] 팀 협업 도구나 방법론 언급 (Git Flow, Agile, 코드 리뷰 문화 등)
- [ ] 읽는 사람이 궁금해할 만한 질문을 자연스럽게 유도
  - 예: "마이크로서비스 아키텍처로 전환" → 면접관이 "왜 전환했나요?" 물어볼 가능성

---

## ✅ 평가 체크리스트 (검증 방법)

### 자가 점검
1. 기술을 모르는 친구에게 읽어주고 "이 사람이 뭘 만들었는지" 설명할 수 있는가?
2. 면접관 입장에서 "다음에 물어보고 싶은 질문"이 떠오르는가?
3. 3개월 후 내가 다시 읽어도 당시 상황이 기억나는가?

### 타인 검증
- [ ] 동료 개발자에게 리뷰 요청 (기술적 정확성)
- [ ] 비전공자에게 읽어보게 함 (가독성, 이해도)

---

## 📝 작성 예시

### ❌ Before (개선 전)
```
React를 사용한 쇼핑몰 프로젝트에 참여했습니다. 
프론트엔드 개발을 담당했습니다.
```

### ✅ After (개선 후)
```
월 평균 방문자 5만 명 규모의 반려동물 용품 쇼핑몰 웹 프론트엔드 개발 (3인 팀)
- React + TypeScript 기반 SPA 구조 설계 및 구현
- React Query를 활용한 서버 상태 관리로 불필요한 API 호출 60% 감소
- 장바구니 → 결제 페이지 이탈률을 25%에서 12%로 개선 (UX 개선 및 성능 최적화)
- Lighthouse 성능 점수 48 → 89로 향상 (코드 스플리팅, 이미지 최적화)
```

---

## 💡 핵심 원칙

1. **구체성**: "개선했다" 대신 "40% 개선했다"
2. **맥락**: "React 사용" 대신 "사용자 경험 개선을 위한 SPA 구조로 React 선택"
3. **임팩트**: 기술적 성과 + 비즈니스 성과
4. **진정성**: 실제로 한 일만 작성, 과장 금지
